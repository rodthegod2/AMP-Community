# In-Game End-to-End Test Harness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Run the real Blade & Sorcery game (one instance, through Steam, saves isolated) against a scripted bot peer and verify the multiplayer + mod sync features end to end, unattended, with machine-readable PASS/FAIL output.

**Verified environment (spikes 1–3, see memory note bns-ingame-testing):**
- The game runs only when launched through Steam: `"C:\Program Files (x86)\Steam\steam.exe" -applaunch 629730 <args>` (a direct exe launch exits 53 and Steam relaunches it with the same args; env vars are lost). Steam prepends `-vrmode openvr`; the LAST `-vrmode` wins, so pass `-vrmode mockhmd`.
- Inert hook installed in the real install (Doorstop 4.5, `enabled=false`), enabled per launch with `--doorstop-enabled true --doorstop-target-assembly AmpTestBoot\AmpTestBoot.dll`. AmpTestBoot (`C:\Projects\bns-mp\research\e2e\boot`) redirects `PlatformWindows.rootPath/altPath` to `-amp-test-docs <folder>` (no spaces), sets `AppDomain` data `AMP_TEST_ISOLATED`, and exits 96/97/98 if it can't.
- Working args: `-amp-test-docs <docs> -vrmode mockhmd -skipintro -skipmodswarning -screen-fullscreen 0 -screen-width 640 -screen-height 360 -force-d3d11 -level Home -charindex 0 -logFile <log>`. Home loads and the player spawns ~14 s after start; ~3 GB RAM, ~8 GB VRAM.
- Safety tooling in `C:\Projects\bns-mp\gametest`: `mods-aside.ps1` / `mods-restore.ps1` (move the real Mods folder contents aside and back, verified), `harness.ps1` (`Assert-RealSavesUnchanged` vs `research\e2e\realsaves-snapshot.txt`), `run-steam-test.ps1` (launch + find the Steam-started PID + relaunch watch).

## Safety rules (every task, every run)
- Real saves must stay unchanged except the LastWriteTime of `Saves\steam_autocloud.vdf` (Steam rewrites it on every launch; owner accepted). Check after every run; on any other difference stop everything and report.
- The real Mods folder is always moved aside before a run and restored after (also on failure — use try/finally in the runner); verify against its manifest.
- Only kill processes you started (game PID found after your launch, bot PID). Never kill Steam or other processes.
- Commit check before launching (< 65 GB).
- Never write to the real install except the already-installed hook files; never bypass DRM.
- One build at a time; `-nodeReuse:false -p:UseSharedCompilation=false`; never `dotnet build-server shutdown`.

## Components

### A. Save check exemption (first)
`gametest\harness.ps1` `Assert-RealSavesUnchanged`: ignore ONLY the LastWriteTime of `Saves\steam_autocloud.vdf` (its size, existence and every other file stay strictly checked). Owner approved this exemption explicitly.

### B. Autopilot in AMP (`ModSync/Autopilot.cs`, game code, main thread)
- Active only when `AppDomain.CurrentDomain.GetData("AMP_TEST_ISOLATED") != null` AND the args contain `-amp-autopilot <absolute path to script.json>`. Otherwise it does nothing (zero cost).
- Script: JSON array of steps; state (current step index + scratch values) persisted in `<AMP_TEST_ISOLATED>\autopilot-state.json` so a relaunched game continues where it stopped. Each step logs `AMPTEST STEP <n> <name>` and, when done, `AMPTEST OK <n>`; failures log `AMPTEST FAIL <n> <reason>` and quit with exit code 3; script end logs `AMPTEST DONE` and quits with 0. Every step has a timeout (default 120 s).
- Steps (implement these; keep each small):
  - `waitSpawn` — player in a level (reuse ModSwapClient's in-level check).
  - `host {port, maxPlayers}` — `GUIManager.HostServer(...)` and wait until the local client is connected.
  - `join {address, port}` — `GUIManager.JoinServer(...)`, wait connected (or for the mod sync page).
  - `expectModSync {blocks: bool}` — wait for ModSyncClient.Plan; assert BlocksJoin.
  - `downloadAndRestart {mode}` — call ModSwapClient.DownloadAndRestart(mode) (the game will quit; next start resumes at the next step).
  - `expectRejoined` — after a relaunch: wait until connected again and the mod plan is empty.
  - `expectModFolder {folder, present}` — check `Mods/<folder>` exists or not.
  - `setOption {mod, option, title}` — find ModOption via ModOptionBridge and apply the parameter with that title.
  - `expectOption {mod, option, title}`.
  - `expectProfileActive {active}`.
  - `disconnect`, `wait {seconds}`, `quit`.
- Relaunch under test: when Autopilot is active, the swap helper must relaunch the test the same way (Steam + the same args), not `steam://rungameid`. Add `HelperScript` support for an optional relaunch command line (pure; unit-test the generated script/launcher), and in `ModSwapClient` pass `steam.exe -applaunch 629730` + the original args (from `Environment.GetCommandLineArgs()`, dropping argv[0] and the Steam-injected leading `-vrmode openvr`) when Autopilot is active.
- `AutopilotScript` parsing/validation and state handling go into a pure file (`ModSync/AutopilotScript.cs`) with unit tests in Tests/ModSyncTests.

### C. Bot peer (`tools/e2e/AmpBot`, net472 console, NOT part of the mod)
- References Netamite (`C:\Projects\bns-mp\ampdeps\Netamite.dll`) and compiles the pure AMP files directly (`ModSync/ModEntry.cs, ModInventory.cs, HostModSet.cs, SyncPlanner.cs, MessageChunks.cs, TransferRules.cs, TransferSender.cs, TransferReceiver.cs, ModCache.cs, SettingsRules.cs`) — NOT AMP.dll (its packet handlers need Unity).
- Defines its own packet classes with the SAME ids and field order as AMP's `ModSyncPacket` (MOD_SYNC 111: kind, transferId, part, parts, data) and `ModFilePacket` (MOD_FILE 112: transferId, fileIndex, offset (long), data (string base64)). Netamite finds packets by scanning loaded assemblies; the bot doesn't load AMP.dll, so there is no id clash. Read AMP's packet files and copy field order exactly. Keep a list of any other AMP packets the bot must answer/send to look like a normal peer (e.g. the client's ModList / PlayerData) — only add what the game actually requires (observe logs).
- Modes (args): `--host <port> --mods <folder>` and `--join <address> <port> --mods <folder>`; `--expect <file.json>` with assertions; prints `BOT OK ...` / `BOT FAIL ...` lines and exits 0/1. Implements:
  - Host: on connect send HOST_MOD_SET built from `ModInventory.Scan(--mods)` (platform "windows"); answer JOINER_REPORT; serve MODS_REQUEST with TransferSender (same protocol as ModTransferHost incl. request ids, ack window, READY_NEXT); then greet minimally so the game client considers itself joined (find out by experiment what the AMP client needs after Ready: ServerInfoPacket? Level change? Mirror Server.GreetPlayer's essential packets with the same ids/fields — copy definitions).
  - Join: connect; receive HOST_MOD_SET; plan with SyncPlanner against `--mods`; optionally request downloads and verify with ModCache.Commit; send JOINER_REPORT ready; record SETTINGS_SNAPSHOT / SETTING_CHANGED values; assert per `--expect`.
- Unit-test the bot's protocol pieces against an in-process Netamite loopback where cheap (like nettest).

### D. Test fixtures + runner (`tools/e2e/`)
- `tools/e2e/fixtures/`: small test mods created by a script from the user's real installed mods (copy 2–3 small ones, e.g. JSON-only mods like `Fascia`, `InstantSloMo`, `_TrueZeroEffort`, from the real Mods folder BEFORE moving it aside — read-only copy) plus one synthetic mod (`AmpE2EDummy`: manifest.json + a 1 MB random file + an empty file).
- `tools/e2e/run-e2e.ps1 -Scenario <name>`: build AMP (`build.sh`), stage the test Mods set (test AMP build from `C:\Projects\bns-mp\build` as `MultiplayerMod` + scenario mods) after `mods-aside`, seed a fresh docs folder from `gametest\saves-backup` (one .chr + Options.opt), start the bot, launch the game through Steam with autopilot + test args, tail the game log for `AMPTEST` and the bot output for `BOT` with an overall timeout, then always: stop own PIDs, `mods-restore`, `Assert-RealSavesUnchanged`, print a summary `E2E <scenario> PASS|FAIL`.
- Scenarios:
  1. `host-basic`: game hosts; bot joins with the same mods → bot `ready`, receives ServerInfo/greeting + settings snapshot (contains AMP host settings).
  2. `host-transfer`: game hosts; bot is missing `AmpE2EDummy` → bot downloads it, hash verified, empty file present.
  3. `host-settings`: game hosts; bot joined; autopilot `setOption` MultiplayerMod/PvP → bot receives SETTING_CHANGED with the new title.
  4. `join-download-temporary`: bot hosts with `AmpE2EDummy` extra; game joins → expectModSync blocks → downloadAndRestart Temporary → (helper swap + Steam relaunch with test args) → expectRejoined → expectModFolder AmpE2EDummy present → expectProfileActive true → quit → runner waits for the restore helper (session.json state Restored or gone, helper.log "done") → `Mods` equals the staged test set again (AmpE2EDummy gone from Mods, back in the cache).
  5. `join-identical`: bot hosts the same set → game joins straight through (no mod sync page) → settings snapshot applied.
- A `-All` switch runs every scenario in order and prints a table.

## Execution order
A → B (with unit tests) → C → D scenario 1 → fix → 2 → 3 → 5 → 4 (most complex). After each scenario passes, commit. Every bug found in AMP gets a failing headless test first where possible, then the fix, then the scenario re-run. Push when all pass.
